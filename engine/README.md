# KimiLM engine — technical reference

Python 3.12, FastAPI on `127.0.0.1` (token-protected), SQLite, llama.cpp. Started by the desktop app
(`python -m kimilm serve --data-dir … --resources …` with `KIMILM_TOKEN` in the environment). Until 2.37.0 the
package was called `dva` and its settings `DVA_*`; a setting given by its old name is still read (`kimilm/__init__.py`).

## Modules (`kimilm/`)

| Module | Role |
|---|---|
| `server.py` | HTTP API + server-sent events (`/api/events`) + serves the built UI |
| `app_state.py` | Wires the services; on start, queued follow-ups left from a closed app become "Not sent (the app was closed)"; `start_turn()` saves the user message and starts the turn as a task; `post_message()` handles follow-ups while a chat is busy (`queue` → run right after, `steer` → handed to the running agent at its next step; after Stop they stay unsent); per-chat limits (`chats.settings`) |
| `runner.py` | One chat turn: builds the prompt (harness + project instructions + memory + skills index + summary), runs the harness (chat / agent / planner / research / team loop, or a pipeline), streams events, saves one assistant message with ordered `meta.steps`. `LoopGuard` stops loops in every tool-using turn: exact and near-duplicate calls are refused (searches: ≥60 % word overlap), per-tool caps (web_search 6 by default), a "change approach" note after 3 unproductive results, a forced write-up after 6 (or 5 refused repeats, or the time limit). After a successful change (file written, code run, connector action) earlier reads, listings and runs may be repeated, since their answer can differ; web calls stay blocked |
| `orchestrator.py` | Teams (2.4.0): the planner turns a request into a task graph (goal, done_when, depends_on, role, harness, agent); a scheduler in code starts each task when the tasks it depends on are accepted (respecting agent slots and each model's simultaneous replies), passes their results and a shared team folder to it, and batches finished results into one planner call that accepts, retries with feedback in the same agent chat, messages or pauses running agents, cancels, rewrites or adds tasks, answers questions, or finishes. Agents get `team_board`, `wait_for` and `ask_lead`. Chats, projects and schedules hand multi-step requests to it automatically (`team_mode`: auto / always / off); team harnesses, the team builder and `delegate` always use it. `pause_chat` / `resume_chat` pause any agent loop at its next step (the model is released while paused) |
| `knowledge.py` | Search (2.4.0): project knowledge files (extracted, split into ~1,200-character passages with page/slide/sheet labels, FTS5-indexed), past chats (FTS5 over messages via triggers) and memory relevance; hybrid keyword (BM25) + meaning (cosine) ranking by reciprocal-rank fusion; memory isolation per project; background vector pass while idle |
| `runtime.py` placement (2.4.1) | "GPU" uses a GPU runtime that actually lists a device (`--list-devices`): a CUDA build on a computer without an NVIDIA card is skipped (it used to run everything on the CPU silently); a real card comes before integrated graphics. Per model: layers on the GPU (`-ngl` auto / all / N, the rest on the CPU), context cache on the CPU (`--no-kv-offload`), MoE experts on the CPU (`--cpu-moe` / `--n-cpu-moe N`), vision part on the CPU (`--no-mmproj-offload`), card (`-dev`). After loading, the log's "offloaded N/M layers" and buffer sizes are shown under Loaded now. `Models.tune` ("Find the fastest setup") loads CPU only, everything on the GPU, half the layers on the GPU (and MoE experts on the CPU, or the context on the CPU for real cards) with a short context, measures reading and writing speed, and keeps the fastest writer. Context-memory estimates count only attention layers for hybrid models (`full_attention_interval`, per-layer head counts) |
| Speed (2.4.2) | `Models.suggest` builds a suggested configuration per model from the hardware and, once measured, from "Find the fastest setup" (`Models._tune`: where it runs → writing-thread counts → speculative decoding (ngram-mod, the model's own MTP layers, or a small same-family draft model) on normal and repeated text → follow-up cache reuse). It is applied only by "Use suggested configuration" (`POST /api/models/{id}/suggested`); every setting stays editable. Runtime flags: `-tb` reading threads, `-ctk/-ctv q8_0` compact context memory (forces `-fa on`), `-fa`, `--prio`, `-ub/-b`, `--spec-type`, and for hybrid models `--ctx-checkpoints 8 --checkpoint-min-step 256` so follow-ups re-read only what is new. Prompts keep the system prompt and tool list identical between turns: memory, notes and knowledge passages chosen per request go in a `<context>` block on the latest user message, so llama.cpp reuses the rest from its cache; each reply records `cached_tokens` (`timings.cache_n`) |
| Sequenced runs (2.5.0) | `orchestrator.py`: the planner writes a sequence of steps; code repairs it (a step that names another step depends on it; a planned step with no stated need builds on the one before; order never puts a step before one it needs) and runs one step at a time (`agent_order`: `sequence` \| `parallel`). Each step is a loop: agent → code checks (answer, no error, expected files) → a short strict check against `done_when` (`VERIFY_SCHEMA`) → the same agent again with what is missing, a fresh agent when the objection repeats or the step hung, and after `step_rounds` the best attempt is kept (`partial`) or the step fails; steps that need a failed step are not run. `forecast.py`: prompt measured with llama-server `/tokenize`, growth, calls, output and speeds learned per harness and model in `step_stats`; `Runtime.fit` loads a run's model with the context its largest step needs and one reply slot (`RunFit`, never above the model's own setting), `Runtime.release` unloads a model when no remaining step uses it, `lease(as_loaded=True)` lets memory learning use a model as it is loaded. `llm.py`: every local call is streamed and watched (first-token limit scaled to the prompt and the measured reading speed; `stall_timeout_seconds` between tokens) and raises `LLMTimeout` / `LLMUnreachable` / `LLMContextFull`; `Turn.recover_model` restarts the server and repeats the call once. A failed check, checkpoint or final-answer call falls back to code. Settings: `agent_order`, `step_rounds`, `verify_results`, `plan_approval`, `fit_context`, `unload_after_run`, `stall_timeout_seconds`, `first_token_timeout_seconds` |
| Doing less work (2.6.0) | `snapshots.py`: the model's state after reading a request's system prompt and tool list is saved once per model file, llama.cpp build, context-memory type and prefix text (`--slot-save-path`, `POST /slots/0?action=save`) and restored into a freshly loaded model (`action=restore`) by `LLM.prepare` before the call; a tiny unrelated request before a restore moves the slot's current prompt into llama-server's in-memory cache so it is not overwritten (checked on b12207). One reply slot only; least-recently-used files are deleted above `snapshot_disk_mb`. The system prompt no longer holds the date, the chat's own folder or the conversation summary (they are in the `<context>` block of the latest message), so every chat with the same harness, project and model shares one prefix and one snapshot. `--cache-ram` is always stated (`prompt_cache_mb`, default about 5% of memory, 256 MB to 2 GB; llama.cpp's default allows 8 GB) and half of it is counted in the memory estimate. `Turn.result_limit`: a tool result is cut to about `reading_budget_seconds` of reading at the server's measured speed (2,500 to 24,000 characters; online models keep 6,000). `hardware.py`: `performance_cores()` (Windows `GetLogicalProcessorInformationEx` efficiency classes, Linux `cpu_core`/`cpu_atom` or `cpu_capacity`, macOS `hw.perflevel0`) is the default thread count on processors with fast and slow cores; `keep_fast(pid)` asks Windows not to power-throttle the model server (`SetProcessInformation`, `ProcessPowerThrottling`); a battery or battery-saver note appears under Loaded now. `GET /api/runtime` adds `snapshots` and `cache_ram_mb`; `POST /api/runtime/snapshots/clear` |
| Runs that continue, evaluation (2.7.0) | `orchestrator.py`: `Orchestra.save` writes the run's state (steps, results, log, model sizing) to table `runs` after every start and settled step; a run ends as `done`, `stopped` (Stop) or `interrupted` (crash, or still `running` when the engine starts). `Orchestra.restore` continues one: accepted steps keep their results, a step that was working starts again without counting the cut-off attempt, no new plan and no new user message. `POST /api/chats/{id}/run/resume`, `/run/dismiss`; `chat.open_run` in `GET /api/chats/{id}`; `resume_runs: auto` continues cut-off runs at start (at most twice per run). `lean_kit`: a step of the general agent gets only the tool groups its goal mentions (files always; all groups on a fresh attempt). `step_up`: the same objection twice moves the step to the strongest allowed model. `check_model`: the result check can run on the smallest installed model. Briefs carry a length hint from the measured writing speed (`writing_budget_seconds`) and the planning prompt two example steps. Each step's `used` now splits tokens into read, cached and written, with model calls and tool calls. `evals.py`: twelve offline tasks with code checks (`TASKS`), run as ordinary chats limited to a task folder with approvals off (`origin = eval`: hidden from the chat list, not learned from); results per run in `eval_runs` with version and model; `GET /api/evals`, `POST /api/evals/run`, `/api/evals/stop`. UI: Progress is part of every chat (open by default, remembered, the header button brings it back) and shows what any reply is doing, a continue-run banner, and Settings → Check this setup |
| History and learned model choice (2.8.0) | `GET /api/runs` lists planned runs with what each cost (steps, rounds, model time, tokens read / cached / written); `GET /api/runs/{id}` adds every step's timeline, tools, forecast and the planner's log (`AppState.runs`, `run_detail`; the newest `runs_kept` = 300 are kept). `step_stats` gains `judged`, `passed`, `rounds`: `Forecaster.judge` records a verdict when a step is accepted complete (passed) or is exhausted, kept incomplete or moved to a stronger model (not passed). `Forecaster.choose` picks the model of a step whose model nobody fixed (`auto_model`) from those records: the usual model passing under half the time gives way to one passing at least 25 points more; a model passing 80% or more gives way to an equally reliable one that needs under 70% of its time; a model needs three judged steps of that harness to be compared (`learned_model_choice`). `GET /api/models/records` shows the records. Each evaluation run stores the settings it ran with (`eval_runs.settings_json`). UI: Activity → Planned runs and Models' record; Settings → Check this setup has a model picker, a two-run comparison and CSV export |
| Long-running tasks, set-ups, browser tools (2.9.0) | `missions.py`: `Mission(Orchestra)` is a run whose steps are decided one move at a time. The planner keeps an `understanding` (rewritten every move); `advance` runs when every step is settled: it records the handoffs (`parse_handoff`: the `## Handoff` block with Done / Found / Next that every agent's brief asks for), checks the limits, and asks for the next move (`move_schema`: understanding, changed, reason, decision continue / finish / ask, one or two steps, outline). Each step runs in a fresh agent chat whose brief holds the understanding, one line per earlier step and the last handoff in full; results are checked like any step. A planner call that fails falls back on the last handoff's Next; twice in a row pauses. Limits (`hours`, `steps`, `step_minutes`, `tokens`, `cost`) pause the task between two steps (`runs.status = paused`, `state.mission.pause`), as does a question to the user; `PUT /api/missions/{run}/limits` changes them, `POST /api/chats/{id}/run/resume` or a new message in the chat continues (`open_mission`, `Mission.restore`, `came_back`). A task cut off by a restart continues by itself (`mission_auto_resume`; at most three times since its last accepted step). `orchestrator.py` gained the hooks this needs: `advance`, `over_limit`, `extra_state`, `load_extra`, `kind` (column `runs.kind` = run or mission). Harness mode `mission` (built-in `long-task`); `Turn.run_mission`. Set-ups: `plan_setup` turns a sentence into a proposal (written-out goal, done_when, kind, team, limits, allow, outline; with `scheduled` also when) and `clean_setup` repairs it; `POST /api/missions/plan` returns it without saving or starting anything; `POST /api/missions` starts a task, `GET /api/missions` lists them. Unattended policy: `allow` (tool groups in `missions.ALLOWABLE`) is stored as `chat_policy:<chat>` and passed to every agent of the run; `Turn.approve` lets those groups through and asks (and notifies) for everything else; sending files online is never covered. Scheduled tasks carry a set-up (`schedules.setup_json`): kind `mission` starts a long-running task, `allow` applies to a plain run too; a run that could not start is logged. Browser tools (`tools/browser.py`, group `browser`): `browser_open`, `browser_look`, `browser_click`, `browser_type`, `browser_select`, `browser_press`, `browser_screenshot` drive the Playwright MCP helper; `services.BrowserSession` keeps one page per chat open between calls (closed after 15 idle minutes); every action answers with the page as it is afterwards; downloads started by a click are moved to the chat's `downloads` folder; the helper now writes to `<data>/browser` (`--output-dir`). `max_native_tools` default 28 → 36 (migrated once) because the tool list grew by seven. `GET /api/busy` tells the shell what is running: it keeps the computer awake meanwhile (`powerSaveBlocker`, Settings). UI: Long-running tasks page (set-up card, limits, continue), the planner's set-up in the schedule editor, the task's understanding and limits on the plan board |
| MCP servers set up like in other apps (2.10.0) | `mcp_config.py`: `parse` reads the configuration shapes of other apps (`mcpServers`; VS Code's `servers` and JSON with comments; Zed's `context_servers`; `serverUrl` / `httpUrl`; `disabled`; the `mcp-remote` bridge, read as the remote server it points at with OAuth), `find_configs` finds such files on this computer (Claude Desktop, Claude Code incl. per-project servers, Cursor, VS Code, Windsurf, LM Studio, Gemini CLI, Zed), `export` writes KimiLM's connectors as `mcpServers` with `${NAME}` references instead of secrets, `expand_vars` fills `${NAME}`, `${env:NAME}`, `${NAME:-default}` when a server starts. `mcp.py`: connectors have `type` (stdio, http = Streamable HTTP, sse), `headers`, `cwd`; values of `env` and `headers` live in the credential store (`connector_values:<id>`), the database keeps the names; auth is none, bearer, headers or `oauth` (fastmcp's OAuth client: browser, local callback, tokens under `<data>/mcp-auth/<id>`; a `.ok` marker after the first successful sign-in; a session that is not interactive never opens a browser). The client library (fastmcp 4.1.8, MCP SDK 2.3.0) negotiates protocol `2026-07-28` (stateless, `server/discover`) or an earlier revision; `Session._describe` keeps the server's name, version, protocol and capabilities (`connectors.info_json`), `list_tools` adds counts of resources and prompts. Tools carry `title` and `destructive`; a server's own read-only hint decides, the tool's name only when there is none. `result_text` saves returned images, audio and files under the chat's `connector-files`. Resources and prompts: `Connectors.resources`, `read_resource`, `prompts`, `prompt`; agents get `list_connector_resources` and `read_connector_resource` when a connected server really has resources. `resolve_command` names what to install when a command is missing; `node` and `python` fall back to the app's own. Online models are not held to `max_native_tools`. Plugins: `plugin.json` may list servers under `mcpServers` (`${__dirname}`, `${user_config.key}`, `${setting}`); an MCP bundle (`.mcpb`: `manifest.json` + files) installs as a plugin (`bundle_to_plugin`: `user_config` → settings, sensitive ones as secrets; `platform_overrides`; node / python / uv / binary). Routes: `GET /api/connectors-found`, `POST /api/connectors-preview`, `POST /api/connectors-import` ({text} or {path, app, names}), `GET /api/connectors-export`, `POST /api/connectors/{id}/signout`, `POST …/prompt`, `GET …/resource`; `…/test` now returns `info`, `resources`, `prompts`. UI: Connectors tab with Paste a configuration, Found on this computer, Export, Edit, Sign in / Sign out, the server's identity and protocol, resources and prompts |
| Pictures (2.11.0) | `images.py`: `Images` is the media layer for pictures. **Engine**: stable-diffusion.cpp at the release pinned in `versions.json` (`sd_cpp_tag`), installed per backend into `<data>/runtimes/sd-<backend>` (`install_engine`: the release's file list from GitHub, the known Windows file names when that list cannot be read, the CUDA runtime files for CUDA); `KIMILM_SD_CLI` points at a build of your own. `choose_engine`: the setting `image_compute` (auto, cpu, vulkan, cuda, metal); auto takes a graphics-card build only when a card that is not integrated is found. **One job at a time, one memory budget**: `_local` asks the text-model runtime to unload idle models (`runtime._make_room`) and runs `sd-cli` once per request (model files by slot: `-m`, `--diffusion-model`, `--llm`, `--vae`, `--clip_l`, `--clip_g`, `--t5xxl`; `-p -n -W -H --steps --cfg-scale -s -b -o`; a change is `-r` for models that follow an instruction about a picture, else `-i --strength` and `--mask`; `--vae-tiling` above one megapixel; the model's own extra options); the process ends and its memory is free. Progress is read from the program's `step/steps` lines; `_explain` turns its last lines into a plain message; `image_timeout_minutes` stops a request. **Models** (table `image_models`): `local` (files by slot, used where they are) or `online`; `RECIPES` name the parts of recommended models and where they are published, `pick_file` chooses the file from the repository's listing when it is downloaded (`<models>/image/<recipe>/`). **Online**: OpenAI (`/images/generations`, `/images/edits` as a form with `image[]`) and Google (`models/<id>:generateContent` with `responseModalities: [IMAGE]`, the picture to change as `inlineData`), with the keys of `providers.py`; `online_candidates` reads the provider's own model list; each picture is a `usage` row (purpose `image`, an estimated cost per picture) so the monthly budget counts it. Anthropic is refused with the reason (Claude reads pictures, it does not make them). **Records**: every picture is a file and a row in table `media` (prompt, model, seed, settings). **Tools** (`tools/images.py`, group `images`, offered when an image model is ready): `generate_image`, `edit_image`; files go to `images/` of the chat's first folder; a step's pictures travel as `media` on the tool step and the `tool_result` event; an online image model asks first (`use_online_image_model`, once per chat with Always). Harness `illustrator`. Routes: `GET /api/images`, `PUT /api/images/settings`, `POST|DELETE /api/images/engine`, `POST|DELETE /api/images/recipes/{key}/download`, `GET /api/images/online/{provider}/models`, `POST|PUT|DELETE /api/images/models`, `POST /api/images/generate` (a background job, event `image_job`), `DELETE /api/images/jobs/{id}`, `POST /api/images/upload`, `GET|DELETE /api/images/library`. UI: Images (Create, Library, Models), pictures inside chat steps with a large view and download. Tests use `tests/fake_sd_cli.py`, which accepts exactly the options read from the program's source at the pinned release |
| Sound (2.12.0) | `sound.py`: `Sound`. **On this computer** the models run in `sound_worker.py`, a process per request (`python -m kimilm.sound_worker job.json`; JSON lines on stdout: progress, then `done` or `error`) with the sherpa-onnx library (`requirements.txt`, pinned 2.0.1: ONNX models on the processor). Jobs: `speak` (segments with a model each: Kokoro, Kitten and Piper by speaker number, Pocket TTS with a reference recording; one WAV and where each segment starts) and `transcribe` (Whisper; the recording is cut where nobody speaks with Silero VAD, each piece padded a little so first and last words are whole; text and timed segments). `KIMILM_SOUND_WORKER` replaces the worker (tests), `KIMILM_SOUND_LIBRARY` names the library version. **Pronunciation**: the library's 2.x versions dropped espeak-ng (GPL), so `espeak()` is false and models that need it are not offered (`needs_espeak`: Kitten, Piper voices, Kokoro's languages other than English and Chinese); with a 1.x version installed they are. English text is prepared by `spell_english` (numbers, years, money, signs as words), because a dictionary-based voice skips what is not a word. **Models** (table `sound_models`, roles tts / stt / music / clone): `CATALOG` (downloads from the library's own GitHub releases, unpacked into `<models>/sound/<key>/`), `add_folder` (a model folder already here), `add_online`. **Voices**: speakers of installed models, providers' voices, and voices from recordings (table `voices`; `create_voice` needs `consent`: `mine` + confirmed, or `other` + the person + a consent recording, kept under `<data>/voices`; at least 5 seconds; stored as 24 kHz mono, at most 30 s). `speak`: `parse_script` reads `Name: text` lines; speakers without a chosen voice get different ones; consecutive lines of local voices are one worker job, lines of an online model are requests to the provider (Google: one request for a dialogue of two of its voices), and `_join` puts the parts into one file (`write_audio`: wav, mp3, m4a through PyAV; wav when a format cannot be encoded). **Online**: OpenAI `/audio/speech` and `/audio/transcriptions`; Google `/v1beta/interactions` for speech (`generation_config.speech_config`, `speech_metadata` annotations) and music (Lyria: length, lyrics and "no vocals" go into the prompt), `generateContent` with the recording as `inlineData` for transcription (sent as 16 kHz mono mp3); a `usage` row per request (purposes speech / transcription / music; estimated prices per minute or per piece). Anthropic is refused with the reason. `mix`: tracks with volume and start, as long as the first or the longest, fade-out, never clipped. Records: table `media`, kind `audio`. **Tools** (`tools/sound.py`, group `sound`): `speak`, `list_voices`, `transcribe_audio`, `generate_music`, `mix_audio`; each is offered only when a model for it is ready (`hidden_tools`); online models ask first (`use_online_sound_model`). Harness `sound-producer`. Routes: `GET /api/sound`, `PUT /api/sound/settings`, `POST|DELETE /api/sound/catalog/{key}/download`, `GET /api/sound/online/{provider}/{role}/models`, `POST|PUT|DELETE /api/sound/models`, `POST|DELETE /api/sound/voices`, `POST|DELETE /api/sound/jobs` (speak, transcribe, music, mix; event `sound_job`), `POST /api/sound/upload`, `GET|DELETE /api/sound/library`. UI: Sound (Speak, Transcribe, Music, Library, Voices & models), players inside chat steps, Read aloud on replies and Dictate in the composer (`components/Audio.tsx`) |

| What is happening, and video (2.14.0) | **Every piece of background work is a task** (`jobs.py`): chat replies, scheduled and long runs, pictures, sound, video, downloads and installs. A task keeps a **trail** (`Jobs.trail`: `<data>/jobs/<id>.trail`, one JSON object a line: kind `step` | `output` (a line a program printed) | `note` | `error`, with its time; event `job_trail`), a **plan** (`Jobs.plan`: `<id>.detail.json`: `stages` + `stage`, and one object per part of the work: `picture`, `picture_run`, `speech`, `podcast`, `episode`, `script`, `music`, `video`, `video_run`, `clip`, `edit`; `None` takes a part away; event `job_detail`), a **fraction** when known and **`quiet`**: the seconds since its last sign of life while it runs (`GET /api/jobs?status=&kinds=`, `GET /api/jobs/{id}` with `trail`, `detail`, `quiet`, `fraction`). Work reports through `Jobs.reporter(on_status, job_id)` → `(status, track)`: `status(text)` is a step, `status.beat(text)` a moving counter (shown, not kept), `track.stages/at/plan/note/output`. `Jobs.follow(kind, title, work, state, stop)` runs work that keeps a state of its own (text, image, sound and video model downloads; the three engine installs) as a task: the state is read once a second. `Images.start_job`, `Sound.start_job`, `Video.start_job` create tasks (`job_id` in the window's job). ## Formats

**Skill** — a folder with `SKILL.md`:
```markdown
---
name: monthly-report
description: Use when writing the monthly project report.
---
Steps and rules in Markdown. Extra files in the folder can be read with read_skill_file.
```

**Harness** — a folder with `harness.json` (+ optional `prompt.md`):
```json
{"name": "Proofreader", "description": "…", "type": "loop", "mode": "agent",
 "tools": ["files", "memory", "skills"], "connectors": false, "max_steps": 6, "temperature": 0.2,
 "thinking": false, "tool_mode": "native", "memory": true, "learn": true}
```
`mode`: `chat` (no tools), `agent` (tool loop), `planner` (JSON plan → steps → answer), `research` (code-driven:
plan queries → search → rank (official sources first, max 2 pages per site) → read in parallel → extract facts per
page (JSON) → download data files/PDFs → cited report; notes in `workspace/research/<time>/`; options `queries`,
`pages`, `max_downloads`), `team` (a lead splits the request into agents — child chats with their own harness, model
and limits — runs them in parallel, then combines). `tool_mode: "json"` uses grammar-constrained decisions for
models that fumble native tool calls. Limits: `max_reply_tokens`, `max_tool_calls`, `max_searches`,
`time_limit_minutes`, `tool_limits: {"web_fetch": 10}`. Chats can override these (`chats.settings`).

Built-in harnesses: Chat, Agent, Planner, Researcher (research mode), Data analyst, Coder, Writer, Document reader,
Vision analyst, Team lead.
Pipeline harnesses run code: `{"type": "pipeline", "entry": "run.py", "args": ["run"], "args_map": {"topic": "--topic"},
"inputs": {JSON schema}, "input_prompt": "…", "needs": ["browser", "model"], "timeout_minutes": 60}`. The entry
prints progress lines, optional `::progress {"text": …}` and one `::result {"summary_markdown": …}`. With
`needs: model` it gets `KIMILM_LLM_API=openai`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`; with `browser`,
`KIMILM_BROWSER_MCP_URL`.

**Plugin** — a folder with `plugin.json`: `id`, `name`, `version`, `description`, `settings[]`
(`text|secret|select|boolean|textarea|folder`; secrets go to the credential store), `connectors[]` (`http` with
`auth: {type: bearer, setting: <key>}`, or `stdio` with `command`/`args`; `{node}`, `{python}`,
`{playwright_mcp}` placeholders), `setup` (a script returning `::result {ok, message, settings, options}`),
`actions[]`, `schedule_templates[]`, plus `skills/` and `harnesses/` folders. Scripts receive
`KIMILM_PLUGIN_SETTINGS` (JSON incl. secrets), `KIMILM_PLUGIN_DATA`, `KIMILM_PLUGIN_DIR` (and, for scripts written
before 2.37.0, the same under their old names `DVA_PLUGIN_*`).

## No built-in plugin (2.15.0)

KimiLM ships without plugins. A sample plugin lives in `tests/plugins/sample`, where the test suite installs it the
way a user installs a plugin (a folder in the data folder's `plugins`), to exercise settings, a set-up script, a
pipeline harness and a plugin's connector. Online services are added as connectors (Plugins & connectors → Add
connector).

## Safety model

- Engine listens on 127.0.0.1 only, requires the per-launch token, rejects other Host headers (DNS rebinding).
- llama-server listens on 127.0.0.1 with its own random API key.
- File tools only touch granted folders + the chat workspace; deletes are moved to `.trash`; edits keep `.backups`.
- Anything that changes something (writes, Python, schedules, connector tools without `readOnlyHint`) asks first,
  unless the chat or scheduled task turns on auto-approve. Unanswered approvals decline after a timeout.
- Memory refuses key/password/card-number-like text. Secrets never return to the UI after saving.
- `run_python` and `run_command` (PowerShell on Windows, no input, timeout) are not sandboxed (it is the user's own
  computer); they are off-able in Settings ("run code") and always ask unless the chat auto-approves.
- Memory isolation: a project with memory_mode "isolated" sees only its own chats, notes, files and memory; its chats
  never appear in other chats' searches (the user's own sidebar search still finds them).
- Online models (`cloud_privacy`): **ask** (default) — before an online model first sees memory notes, attachments
  or anything read from files, folders, images or Python output, the turn asks (`send_to_online_model`, never
  auto-approved); "Keep it on this computer" switches the turn to a local model. **local_unless_on** — online only in
  chats switched on. **auto** — no prompt. Pipelines and memory learning always use local models. API keys live in
  the OS credential store and are never returned to the UI.

```powershell
cd engine
.\.venv\Scripts\python.exe -m pytest -q tests\test_engine.py
```
